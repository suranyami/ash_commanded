<objective>
Make every verifier in this library provably load-bearing: rewrite the seven mocked verifier tests
so they reach the verifier through real DSL compilation, add the two event-handler verifier tests
that have never been collected by `mix test`, and delete the one test file whose only assertion is
that modules exist.

fixed structs into the real `verify/1`. That tests the verifier's logic — which is worth something —
but it cannot fail if the verifier is removed from the extension's verifier list, because the test
calls `verify/1` directly. TEST-02 and SC3 are specifically about the compile-time path.
Output: nine verifier test files that all fail loudly when their verifier stops running.
</objective>

    Rewrite all four files to the D-14 pattern. Delete `import Mock` and every `with_mock` block; the
    verifier must be reached through real compilation, not through mocked introspection.

    **The pattern (D-14).** Each rejection test wraps a `Code.compile_string/1` call in
    `assert_raise Spark.Error.DslError, ~r/.../`. The string is a heredoc containing a complete
    `defmodule` that uses `Ash.Resource` with `domain: nil` and `extensions:
    [AshCommanded.Commanded.Dsl]`, an `attributes` block with `uuid_primary_key :id` plus whatever
    attributes the case needs, and a `commanded` block carrying exactly the malformation under test.
    Interpolate `System.unique_integer([:positive])` into the module name so the test is safe under
    `async: true` and repeated runs — Elixir's module namespace is global per VM.

    Keeping the bad DSL as a string rather than as a nested `defmodule` is the point of D-14: no
    malformed DSL ever sits in a compiled file, so the test file itself always compiles.

    **The regex.** Derive it from the verifier's own message construction, which you read in
    `<read_first>`. Match the distinguishing fragment — the offending command name, the duplicate
    field, the unknown action — not the full message. A full-string match would break the first time
    Spark reformats its error envelope, and REPO-03 bumps Spark from `~> 2.3` to `~> 2.6`, so that
    reformatting is a live possibility inside this very phase.

    **If Spark wraps the error.** If compilation surfaces something other than a bare
    `Spark.Error.DslError` (a `CompileError` carrying it, for instance), do not weaken the assertion
    to a bare `assert_raise` — assert on the wrapper type AND assert the message fragment is present
    in the raised exception. Record what actually surfaced in the SUMMARY, because the other five
    verifier tests in Task 2 and Task 3 must use the same shape.

    **The accepting tests.** For each file, add a test that compiles the well-formed counterpart and
    asserts no error is raised, and a test that compiles a resource with the relevant DSL block
    present but empty and asserts no error is raised. Without these, a verifier that rejected
    everything would pass every rejection test — the rejecting test alone cannot distinguish a
    correct verifier from a broken one.

    Each file keeps `use ExUnit.Case, async: true`. Remove the `@moduletag :verifier_test` — it was
    only there to serve `run_tests.sh`'s artificial file split, which Plan 01-07 deletes, and
    `test_helper.exs` never excluded it, so it currently means nothing.

<threat_model>

## Trust Boundaries

| Boundary | Description |
| --- | --- |
| consumer's DSL source → compiled resource | The verifiers are the only place a malformed or hostile DSL declaration is rejected before it becomes generated, executable code. A verifier that is declared but never runs is a check that exists only on paper. |
| test-supplied DSL string → `Code.compile_string` | The rejection tests deliberately compile malformed source at test runtime. The strings are authored in this repository and interpolate only a unique integer. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
| --- | --- | --- | --- | --- | --- |
| T-01-13 | Tampering | The nine verifiers in `lib/commanded/verifiers/`, as reached from `lib/commanded/dsl.ex`'s verifier list | high | mitigate | Mocked tests called `verify/1` directly and so could not detect a verifier dropped from the extension's list — the exact failure mode by which a declared validation silently stops running. Rewriting every test to reach the verifier through real compilation, plus the per-verifier commented-out check in Task 2, is the mitigation. |
| T-01-14 | Tampering | `Code.compile_string/1` in the test suite | low | accept | The compiled strings are literals authored in this repository with a single interpolated integer; no test input is read from a file, an environment variable or a network source. Compiling attacker-controlled source would be a different design, and is not proposed. |
| T-01-15 | Repudiation | Deletion of `integration_test.exs` and `event_handler_tests.exs` | medium | mitigate | Both deletions are recorded in the SUMMARY with the assertion each file made and the reason, and the plan carries a prohibition against deleting a test for being inconvenient. The audit trail is what distinguishes triage from shrinking the suite until it is green. |
