generated aggregate module that really compiles, through `CommandActionMapper`'s real Ash execution
path, into a real record in a real (ETS) data layer, read back and asserted. Then extend that proven

reason. If the tracer does not work end-to-end, nothing built on top of it is trustworthy, and this
plan is the cheapest place to discover that.

execution paths, and two tests that assert real persisted state.

<threat_model>

## Trust Boundaries

| Boundary | Description |
| --- | --- |
| dispatched command → Ash action | Command parameters cross from the caller into `Ash.Changeset.for_action/3`. Until this plan, the test branch returned them unvalidated; after it, Ash's own attribute constraints re-validate every parameter. |
| test fixture → ETS table | The Widget fixture's process-scoped ETS table is the only persistence surface introduced. It is in-memory, per-process, and never leaves the VM. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
| --- | --- | --- | --- | --- | --- |
| T-01-03 | Tampering | `CommandActionMapper.execute_create/4`, `execute_update/5`, `execute_destroy/5` | high | mitigate | Removing the test branch is itself the mitigation: a mock that echoed parameters back bypassed `ParameterValidator` and Ash's own attribute constraints entirely, so the validation layer shipped untested. After this plan every parameter crosses `Ash.Changeset.for_action/3` and is re-validated by Ash — defence in depth that previously existed only on paper. |
| T-01-04 | Tampering | `Ash.Query.for_read` lookup action in the update and destroy paths | high | mitigate | The lookup previously named an action no resource declares. Pinning it to `:read` means update and destroy resolve their target record through a declared, policy-checkable action rather than raising, so a consumer's Ash policies can actually apply to the lookup. Verified by a negative grep for the old atom plus a positive count of two `for_read(:read)` sites. |
| T-01-05 | Spoofing | Command `identity_field` used to locate the record to mutate | low | accept | The command's id field is the only record selector; there is no authorization layer in this library (command authorization is the consuming application's Ash policy layer, unchanged by this phase). Out of scope per CONTEXT.md — Phase 2 owns the missing name-conflict verifier (QUAL-06). |

</threat_model>
