<objective>
Make each of the five gates provably alive in two different senses: a permanent regression test that
its detection logic still fires, and a one-time, human-readable record that the real `mix check`
actually failed on a real violation and went green when it was removed.

Purpose: ROADMAP success criterion 3 states five deliberately-seeded violations must each fail
`mix check` with a message naming the file and rule, and that removing each turns the build green
again. Read strictly that is a one-time exercise; read as engineering it is a permanent property.
RESEARCH.md's Open Question 4 concludes both are needed and neither alone suffices.

Output: five fixtures and a meta-test over them, a phase-citation test that expires every suppression
with its phase, and a committed gate-evidence document.
</objective>

WHERE THE FIXTURES LIVE, AND WHY. Put all five under `priv/seeded_violations/`. That directory is on
neither `elixirc_paths` list nor any Credo `included:` glob, and it is not swept by test discovery, so
a file there encodes a genuine violation forever without being compiled, linted or run. Do not put

glob and test discovery would both reach them.

THE FIVE FIXTURES. Model each on the parity fixture's minimalism and push exactly one dimension past
its limit, so a failure names one rule rather than several:

1. A module with a single function clause spanning more than 10 rendered lines, shaped like rendered
   generator output rather than like generator source, since that is what the FOUND-06 gate measures.
2. A module containing a `quote` block longer than 40 lines, shaped like generator source, since that
   is what FOUND-07 measures.
3. A module whose body reassembles a compile-time-known list at runtime, the FOUND-08 defect class,
   again shaped like rendered output.
4. A transformer-shaped module that builds AST from an interpolated string, the FOUND-09 class.
5. A module that derives a module name by splitting another module's name and reconcatenating it, the

Give each fixture a top comment naming the gate it exists to trip and stating that it is deliberately
invalid and deliberately uncompiled.

## Trust Boundaries

| Boundary                                 | Description                                                                                    |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------- |
| suppression to the phase that removes it | A disable is a deliberate hole in a gate, valid only while its owning phase is outstanding     |
| fixture directory to build               | Files encoding real violations sit inside the repository and must stay invisible to every tool |

## STRIDE Threat Register

| Threat ID  | Category  | Component                                                  | Severity | Disposition | Mitigation Plan                                                      |
| ---------- | --------- | ---------------------------------------------------------- | -------- | ----------- | -------------------------------------------------------------------- |
| T-01-BI-12 | Tampering | a suppression outliving its phase                          | high     | mitigate    | Citation test fails on an absent or completed phase                  |
| T-01-BI-14 | Tampering | a gate's detection logic regressing unnoticed              | high     | mitigate    | Permanent meta-test over five fixtures, run every CI leg             |
| T-01-BI-13 | Tampering | seeded fixtures reached by compiler or linter              | medium   | mitigate    | Fixtures live under a directory on no compile or lint path, asserted |
| T-01-BI-15 | Tampering | a seeded violation left in the tree after the evidence run | medium   | mitigate    | Clean working tree and a final green build are acceptance criteria   |

### Mitigation detail

- T-01-BI-12: this exact decay has already happened once. Every existing disable cites a phase number
  from a roadmap that no longer exists, and nothing detected that. The citation test converts a stale
  comment into a build failure, and the same rule covers staged goldens so the two suppression idioms
  cannot diverge.
- T-01-BI-14: a check whose detection logic silently stops matching looks identical to a clean
  codebase. The meta-test asserts a violation IS found for each gate, and the fixture-count assertion
  means a new gate without a fixture is a failing test rather than an invisible gap.
- T-01-BI-13: the fixtures are deliberately invalid source. Placing them anywhere the compiler or
  Credo reaches would turn the tree permanently red, so both invisibility properties are asserted by
  running the real compiler and the real linter.
- T-01-BI-15: the evidence exercise deliberately breaks the build five times. A leftover seeded
  violation would be indistinguishable from a real regression, so the clean working tree and a final
  green build are explicit acceptance criteria rather than assumed hygiene.

</threat_model>
