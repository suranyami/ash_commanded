<objective>
Turn the one behaviour-unverified item of Phase 1 into an observed fact: watch CI actually run, on a
real remote, and record what it did.

Purpose: `.github/workflows/ci.yml` is well-authored and internally consistent — three legs, pinned
actions, invoking the real `mix check` alias, with a canonical leg matching `test/test_helper.exs`'s
own literal. Phase verification confirmed all of that by reading it. What it could not confirm is
that the workflow has ever executed: `gh run list` returns zero rows on both configured remotes and
the branch carrying this work is pushed to neither. A workflow that has never run is exactly the
"green because it ran nothing" defect class this phase exists to eliminate everywhere else, so it is
recorded as behaviour-unverified rather than passed.

This gap cannot be closed by writing code. It needs a push and a human looking at the result. What
this plan can do first is remove the largest knowable unknown — whether prebuilt toolchain artefacts
exist for all three legs — so that if the run does fail, it fails for a reason worth learning.

Output: an automated toolchain pre-flight, an observed three-leg run, and a committed evidence
record.
</objective>

Establish, with exit codes rather than plausibility, that each matrix leg can obtain a toolchain at
all — the failure that would otherwise consume the first real run.

THE TWO MANIFESTS. The setup action resolves Elixir from the hex.pm Elixir builds manifest and OTP
from the per-runner-OS OTP builds manifest. The key shapes differ and getting either wrong produces
a false negative: the Elixir key pairs the full Elixir version with the OTP *major* only, while the
OTP key carries the full OTP version. Fetch both manifests and, for each matrix leg, assert exactly
one entry matches its key. Assert exactly one rather than at least one, so a prefix-matching mistake
that sweeps in every patch release is visible instead of passing.

Use the runner OS the workflow actually declares, not a guess: read `runs-on` from the workflow file
and resolve which concrete Ubuntu image that currently designates before choosing the OTP manifest
path, since the OTP manifest is published per image and the moving label does not appear in it.

THE VERSION AGREEMENT. In the same pass, assert that the canonical leg's version agrees with
`test/test_helper.exs`'s literal and with `.tool-versions`, and that `mix.exs`'s `elixir:`
requirement admits all three legs. These are local facts, they cost nothing to check, and a
disagreement between them is the second most likely cause of a confusing first run.

IF THE NETWORK IS UNAVAILABLE. Record that outcome explicitly and carry it into Task 2's checkpoint
as an unresolved unknown. Do not mark the pre-flight satisfied on the grounds that it could not run —
a pre-flight that reports success when it fetched nothing is precisely the defect this phase keeps

one.

<threat_model>

## Trust Boundaries

| Boundary | Description |
| --- | --- |
| third-party action to repository token | Actions authored elsewhere execute with whatever token scope the workflow grants |
| external build manifest to CI toolchain | The Elixir and OTP binaries every leg runs are fetched at run time from hex.pm's build manifests |
| CI result to reader | A green tick is read as "the gate ran and passed"; it is only evidence if the gate actually ran |
| pushed branch to public remote | Pushing publishes the working branch and its full history to a remote repository |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
| --- | --- | --- | --- | --- | --- |
| T-01-BI-26 | Tampering | a green run that short-circuited before the later gate steps | high | mitigate | Require the Dialyzer and docs output, which are last in the alias chain, to be observed in each leg's log rather than accepting the job conclusion |
| T-01-BI-27 | Tampering | a leg that silently resolved a different toolchain than it declared | medium | mitigate | Record the resolved Elixir and OTP version per leg from the setup step's own output, not from the matrix entry |
| T-01-BI-28 | Tampering | D-12's canonical split assumed rather than observed | medium | mitigate | Record the per-leg excluded count; the canonical leg must report zero and the others non-zero |
| T-01-SC-07 | Tampering | third-party actions in the workflow | high | accept | Already mitigated by plan 01-06: every action is pinned to a full commit SHA with a version comment, and the workflow grants a read-only `contents` permission at the top level. This plan changes neither, and re-verified the pins while reading the file |
| T-01-ID-07 | Information Disclosure | publishing the working branch to a remote | low | accept | The branch contains only this repository's own source and planning artefacts, all destined for an MIT-licensed public repository; it carries no credential and no third-party data |
| T-01-BI-29 | Tampering | narrowing the matrix to turn a red leg green | high | mitigate | The plan forbids it: a failing leg is recorded and reported, and whether to reduce the supported range is escalated rather than decided inside a gap-closure plan |
| T-01-SC-08 | Tampering | dependency supply chain | low | accept | This plan installs no package and changes no entry in `mix.exs` deps or `mix.lock`. The package-legitimacy gate has nothing to audit here |

### Mitigation detail

- T-01-BI-26 is the single most important line in this threat model, because it is the exact defect
  class this phase was created to eliminate and the one a CI badge is best at hiding. A job
  conclusion tells you a process exited zero. Seeing output from the last step in the alias chain
  tells you the chain ran.
- T-01-BI-29 is recorded as a threat rather than as a note because the cheapest way to make this
  plan "succeed" is to delete the failing leg, and that converts a finding about the supported
  version range into a quietly weaker promise nobody agreed to.
- T-01-SC-07 is carried forward rather than re-mitigated: plan 01-06 pinned every action to a full
  SHA and set a read-only workflow-level permission, and this plan's reading of the file confirmed
  both still hold. It is listed so a reviewer does not have to wonder whether it was considered.
