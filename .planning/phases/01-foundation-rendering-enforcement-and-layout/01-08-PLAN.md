<objective>
Stop caller-supplied command parameter data from minting new atoms, and record the trust boundary
that replaces it.

Purpose: `cast_value/2`'s `:atom` clause converts an arbitrary binary into an atom by the unbounded
route. Atoms are never garbage collected on the BEAM, so an unbounded stream of caller-controlled
strings exhausts the atom table and takes the node down. The value being cast is a command
parameter, which in any real Commanded application originates outside the system. This is CR-03 in
`01-REVIEW.md`, recorded there as deferred to this plan because it is a behaviour change to shipped
command dispatch with no test coverage in Phase 1's scope. It is pre-existing — no Phase 1 plan
introduced it — and it ships today.

Output: a decided and recorded trust boundary, the cast rewritten against it, a test that observes
the atom table rather than the return value alone, and a documentation example that no longer
teaches the defect.
</objective>

  <decision>Which trust boundary replaces unbounded atom creation when `cast_value/2` is asked to cast a binary to the `:atom` type?</decision>
  <context>
The current clause converts any binary into an atom. Atoms are never reclaimed on the BEAM, so a
stream of caller-controlled strings exhausts the atom table and takes the node down. The function is
reached from `ParameterTransformer.transform_params/2`, which is public, documented and separately
tested, and from `CommandActionMapper` on the dispatch path whenever a command carries a non-empty
transform list.

Whatever is chosen becomes the library's stated trust boundary for atom casting, which is why it is
decided once, in the open, before any code moves. It is also a behaviour change to shipped dispatch:
a caller that relied on new atoms being minted starts receiving errors. PROJECT.md's Key Decisions
license breaking freely while the library is on 0.x, and it is at 0.2.0, so the constraint is
honesty about the change rather than compatibility with the old behaviour.

Recommendation: **Option A**, with the error message naming the field and the expected type rather
than echoing the rejected value (see Task 2's threat note T-01-ID-05). The migration note belongs in
the changelog, not in a compatibility shim.
  </context>
  <options>
    <option id="existing-atoms-only">
      <name>A — existing atoms only, error tuple otherwise (recommended)</name>
      <pros>One clause changes. Matches the boundary Ecto and Ash already hold at their own edges, and the boundary a reader expects from a library that accepts external data. Fits the existing contract exactly: every other cast type already returns an error tuple for unparseable input.</pros>
      <cons>A consumer relying on new atoms being minted from caller data starts receiving errors. That is the intent, but it is a real behaviour change to shipped dispatch and belongs in the changelog.</cons>
    </option>
    <option id="resource-derived-allowlist">
      <name>B — allow-list derived from the resource's own attribute and action atoms</name>
      <pros>More precise than A: rejects a binary that happens to collide with some unrelated atom the runtime loaded for another reason.</pros>
      <cons>`cast_value/2` receives only a value and a type and has no resource context, so this requires threading resource context through `transform_params/2` — a signature change to a public, separately tested function. The precision gain is unusable by any current caller, because the DSL block that would declare these casts does not exist (see plan 01-09).</cons>
    </option>
    <option id="configurable-strictness">
      <name>C — configurable strictness with a documented default</name>
      <pros>Leaves an escape hatch for a consumer who genuinely needs to mint atoms from caller data.</pros>
      <cons>A knob defaulting to lax ships the defect by default and is not a fix. A knob defaulting to strict is Option A plus an escape hatch nobody has asked for, and an escape hatch from a security boundary is a liability until someone demonstrates they need it.</cons>
    </option>
  </options>
  <resume-signal>Reply with `existing-atoms-only`, `resource-derived-allowlist`, or `configurable-strictness`</resume-signal>
  <done>The trust boundary is chosen and recorded, with the reasoning written down, before any dispatch behaviour changes.</done>

<threat_model>

## Trust Boundaries

| Boundary | Description |
| --- | --- |
| external caller to command parameters | An API request, form submission or upstream service supplies the values that become command struct fields |
| command parameters to cast functions | `transform_params/2` applies declared casts to those values; this is where untrusted data first meets a type conversion |
| rejected value to consumer's log pipeline | An error returned from a cast is wrapped by `CommandActionMapper` and surfaces in the consumer's own logging |
| documented example to consumer's own code | A worked example in a library's docs is copied into applications the library cannot protect |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
| --- | --- | --- | --- | --- | --- |
| T-01-DO-02 | Denial of Service | `cast_value/2`'s binary-to-`:atom` clause | high | mitigate | Accept only atoms the runtime already knows; prove it by asserting the atom is still unknown after a rejected cast, not by asserting the return value |
| T-01-DO-03 | Denial of Service | the same pattern reproduced in consumer code from this module's worked example | high | mitigate | Rewrite the example to the boundary the library holds and state the reason beside it |
| T-01-ID-05 | Information Disclosure | rejected caller data echoed verbatim into the consumer's logs through the error message | medium | mitigate | Name the expected type and the field; never interpolate the rejected value |
| T-01-DO-04 | Denial of Service | `transaction.ex`'s atom derivation from a command module name | low | accept | Input set is bounded by the command modules the application compiled; no caller-supplied string reaches it. Assessment recorded in a comment at the site so it is not re-derived |
| T-01-BI-21 | Tampering | a security fix whose test cannot distinguish "rejected" from "created then rejected" | high | mitigate | The test observes the atom table directly after the call, which is the only assertion that separates the two |
| T-01-SC-05 | Tampering | dependency supply chain | low | accept | This plan installs no package and changes no entry in `mix.exs` deps or `mix.lock`; the replacement uses a function already in the Elixir standard library. The package-legitimacy gate has nothing to audit here |

### Mitigation detail

- T-01-DO-02 is the finding this plan exists for, and its severity is `high` against the configured
  `security_block_on` threshold precisely because the affected function sits on the command-dispatch
  path this library exists to provide. Its reachability is not hypothetical:
  `ParameterTransformer.transform_params/2` is public, documented and separately tested, so a
  consumer reaches it directly regardless of what the DSL does or does not currently declare.
- T-01-DO-03 is rated equal to T-01-DO-02 deliberately. A library that fixes a defect in its own
  code while continuing to demonstrate it in its documentation has moved the vulnerability from one
  codebase to every codebase that copies the example, which is a worse outcome than leaving it in
  one place.
- T-01-ID-05 exists because the obvious fix — returning an error that inspects the offending value —
  converts a rejected input into an attacker-chosen log payload of attacker-chosen length. The
  message names the shape that was expected, not the data that arrived.
- T-01-BI-21 is this phase's recurring defect class applied to a security fix. `assert {:error, _}`
  passes identically whether the atom was created or not. Only checking the atom table afterwards
  tells the two apart, which is why it is written as a required assertion rather than a suggestion.

</threat_model>
